# LumiRose v1.1 实现计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 按 `docs/requirements/v1.1.md` 在 v1 的库上补齐流式、取消、重试、同会话串行化、上下文裁剪、结果与遥测、仓储契约与 README，且 v1 公开 API 与 109 个测试保持不变。

**Architecture:** Client 增一条 SSE 传输，边读边装配成与同步响应完全相同的 `ChatCompletionResponseParam`；Agent 把一次运行抽成统一循环，同步与流式只替换“取一轮响应”的传输，决策、工具、提交只有一份；锁、重试、裁剪、遥测作为横切挂在循环外层。全部测试继续走 `FakeServer`，不依赖网络与真实 Key。

**Tech Stack:** Java 21、Maven 3.9、OkHttp 4.12.0、Jackson 2.18.3、SLF4J 2.0.17、JUnit 5.12.2、Logback 1.5.38（仅测试）。

**Spec:** `docs/requirements/v1.1.md`（R33–R69、§11 测试案例 TC-*）

## Review Focus

- SSE 块是纯 `usage`、没有 `choices`：应忽略，不能 NPE — Task 1（TC-ST10）。
- `tool_calls` 分片缺 `index`：应 `CLIENT_RESPONSE_INVALID`，不能 NPE — Task 1（TC-SE07）。
- listener 在 `onStart` 里抛异常：应原样上抛、不发请求、不提交 — Task 3（TC-AS09）。
- 重试发生在工具执行后的第二轮：工具只能执行一次 — Task 4（TC-RT10）。
- 裁剪后请求不得以孤立 `tool` 消息开头 — Task 6（TC-TR08）。

- [ ] **Step 4: 实现 `CompletionStreamListener` 与 `SseAssembler`**

接口按 Interfaces 段。`SseAssembler` 为包内 `final` 类，入口：

```java
static ChatCompletionResponseParam consume(BufferedSource source, CompletionStreamListener listener) throws IOException
```

规则（R35–R38）：逐行读、去行尾 `\r`；空行结束一个事件；多行 `data:` 用 `\n` 拼接；忽略 `:` 注释、`event:`、`id:`、`retry:`；`[DONE]` 结束；只处理 `index == 0` 的 choice；`content` / `reasoning_content` 非空才追加并回调；`tool_calls` 用 `TreeMap<Integer, Slot>` 装配（`index` 缺失 → `ClientException(CLIENT_RESPONSE_INVALID, "流式响应结构非法")`，`id`/`name` 冲突同样）；`finish_reason` 取最后一个非空；`usage` 用 `mapper.treeToValue(node, Usage.class)` 取最后一个非空；EOF 仍无 `finish_reason` → 同一条 2002；`data:` 解析失败 → 2002（不保留 cause，不打印载荷）。装配结果用 `ChatCompletionMessage.builder().role("assistant")...`、`Choice.builder().index(0)...`、`ChatCompletionResponseParam.builder().choices(List.of(choice)).usage(usage).build()`；无内容时 `content` / `reasoningContent` 为 null，无工具时 `toolCalls` 为 null。

- [ ] **Step 3: 实现 RetryPolicy 与重试循环**

`delayMillis`：从 `base` 开始翻倍 `retry-1` 次，超过 `max` 即封顶；`base=0` 恒为 0。Agent 把“取一轮响应”包成：

```java
private ChatCompletionResponseParam requestWithRetry(
        ChatCompletionRequestParam request, int turn,
        CompletionStreamListener adapter, boolean streaming,
        BooleanSupplier delivered, StreamControl control)
```

每次尝试计耗时并调用 `onRequest(turn, ms, success)`（把 Task 2 中“每轮一次”的调用移到每次尝试）；捕获 `ClientException` 后：`!e.retriable()`、`attempt >= maxRetries`、`delivered.getAsBoolean()` 任一成立即重抛；否则 `attempt++`，`delay = RetryPolicy.delayMillis(attempt, base, max)`，`onRetry(attempt, delay, e.getErrorCode().code())`，再 `backoff(delay, control)`。非流式调用 `control` 传 null，`backoff` 只在 `control != null` 时检查取消。`backoff` 按 50ms 分片 `Thread.sleep`，每片检查 `control.isCancelled()` → 抛 `CancelledRun`；`InterruptedException` → 恢复中断标记并抛 `AgentException(AGENT_CANCELLED, "退避等待被中断")`。流式的 `delivered` 由 adapter 在第一次回调前置 true。重试的失败尝试不计入 `turns`。每次重试记 `log.debug("retry: attempt={} delayMs={} code={}", ...)`。
